# 機能別詳細設計フォルダ作成ガイド

バックログから実装可能な詳細設計を作成するための簡潔なガイドです。

## 基本構成・ファイル責務

```
docs/requirement-definition/03-feature/F-XXYY/
├── README.md                # 機能概要
├── 01-requirements.md       # 要件・制約
├── 02-implementation-spec.md # 実装仕様
├── 03-acceptance-criteria.md # 完了基準
└── 90-implementation-report.md # 実装レポート（完了後）
```

| ファイル | 対象読者 | 達成目標 | 読了時間 |
|----------|----------|----------|----------|
| **README.md** | 全員 | **機能の全体像と価値を理解する** | 1分 |
| **requirements.md** | PM・設計者 | **機能の境界と制約を明確にする** | 2分 |
| **implementation-spec.md** | 開発者 | **実装に必要な情報をすべて得る** | 3-7分 |
| **acceptance-criteria.md** | QA・開発者 | **完了の判定基準を共有する** | 2分 |
| **90-implementation-report.md** | 全員 | **実装結果と成果物を記録・共有する** | 2-3分 |

## 重要：重複回避ルール

**DB・API・アーキテクチャは既存ドキュメントを参照するだけ。重複記述禁止。**

| 内容 | 既存定義場所 | 詳細設計での扱い |
|------|-------------|------------------|
| DB設計 | `02-tech/02-database-phase2.md` | リンクのみ |
| API仕様 | `02-tech/03-api-phase2.md` | リンクのみ |
| アーキテクチャ | `02-tech/04-fe・05-be-architecture-phase2.md` | リンクのみ |

## 各ファイルで達成すべきこと

### 📋 README.md の目標
**「この機能がなぜ存在し、誰がどう使うのか」を全員が理解できるようにする**

必要な要素：
- **What**: 機能が何をするか（1行で要約）
- **Why**: なぜ必要か（ビジネス価値）
- **Who**: 誰が使うか（対象ユーザー）
- **When**: いつ必要か（優先度・依存関係）

### 📝 01-requirements.md の目標
**「この機能でやること・やらないこと」の境界を明確にする**

必要な要素：
- **機能スコープ**: 必須機能・オプション機能の切り分け
- **制約条件**: 技術的・ビジネス的制約の明示
- **除外範囲**: 誤解を避けるための「やらないこと」の明記

### 🔧 02-implementation-spec.md の目標
**「開発者が迷わずに実装を開始できる」状態にする**

必要な要素：
- **使用技術・ライブラリ**: 具体的な技術選択
- **既存リソース参照**: 関連するDB・API・アーキテクチャへのリンク
- **実装タスクと工数**: 具体的な作業内容と見積り時間
- **注意点・制約**: 実装時に気をつけるべき事項

### ✅ 03-acceptance-criteria.md の目標
**「いつこの機能が完成したと言えるか」の基準を共有する**

必要な要素：
- **動作確認項目**: 具体的なテストケース
- **品質基準**: パフォーマンス・セキュリティ・アクセシビリティ基準
- **完成定義**: レビュー・ドキュメント・承認の完了条件

### 📊 90-implementation-report.md の目標
**「実装完了後の成果物と結果を記録・共有する」**

必要な要素：
- **実装概要**: 何を実装したかの要約
- **変更内容**: 作成・変更されたファイル・機能の詳細
- **技術検証**: 受け入れ基準の達成状況
- **アーキテクチャ準拠性**: 設計ドキュメントとの適合確認
- **次のステップ**: 後続機能への影響・推奨事項

## 作成時の思考プロセス

### 1. 機能の本質を理解する
- この機能でユーザーの何が変わるか？
- なぜ今この機能が必要か？
- 誰がどのようなタイミングで使うか？

### 2. 境界を明確にする  
- 絶対に必要な機能は何か？
- あれば良いが後回しにできる機能は何か？
- 明確に「やらない」ことは何か？

### 3. 実装に必要な情報を整理する
- 既存のどのドキュメント・リソースを参照すべきか？
- 新しく作成・設定が必要なものは何か？
- どのような順序で実装すべきか？

### 4. 完了基準を具体化する
- どうやって動作確認するか？
- どの品質基準をクリアすべきか？
- 誰がどの段階でレビュー・承認するか？

### 5. 実装完了後のレポート作成
- 実際に何を実装・変更したか？
- 受け入れ基準はすべて満たされたか？
- 設計ドキュメントとの整合性は保たれているか？
- 後続機能開発への影響・推奨事項は何か？

## 記述のポイント

**✅ 良い例（参照重視）**
```markdown
## 使用API
- [商品一覧API](../../02-tech/03-api-phase2.md#商品API)

## 実装内容  
1. ProductCard コンポーネント作成（2h）
   - shadcn/ui Card使用
   - 商品画像・名前・価格表示

2. API連携処理実装（1h）
   - 商品一覧取得
   - エラーハンドリング
```

**❌ 悪い例（重複記述）**
```markdown
## API設計
GET /api/v1/products
Response: { success: true, data: [...] }
```

## 実装完了後の必須作業

### 📊 90-implementation-report.md 作成ルール

**実装完了後は必ず実装レポートを作成する**

**✅ 実装レポートに含むべき内容**
```markdown
# F-XXXX 実装レポート: [機能名]

## 概要
実装した機能の要約（プルリクエスト形式）

## 実装内容
### ✅ [実装項目1]
- 具体的な実装内容
- 作成・変更したファイル

### ✅ [実装項目2]
- 具体的な実装内容
- 技術的な詳細

## 技術検証
### ✅ 受け入れ基準達成
- [x] 動作確認項目1
- [x] 動作確認項目2

### ✅ 品質保証
- [x] 品質基準1
- [x] 品質基準2

## 次のステップ
この実装により可能になった後続機能

## 作成・変更ファイル
### 新規作成
- ファイルパス1 - 説明
- ファイルパス2 - 説明

### 変更ファイル
- ファイルパス1 - 変更内容

---
**ステータス**: ✅ 完了
**レビュー要件**: [レビュー観点]
**デプロイ準備**: [デプロイ状況]
```

**実装レポートの目的**:
- プロジェクト進捗の可視化
- 後続開発者への情報共有
- 設計ドキュメントとの整合性確認
- レビューポイントの明確化

---

**原則**: 読み手の目標達成を最優先に・既存定義の最大活用・具体的な実装指針・完了後の確実な記録
